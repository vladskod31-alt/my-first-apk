# Известные ограничения LIBO 2.8.3 и план работ

Формат записи: ограничение → причина → что сделано сейчас → план. Список обновляется
каждым релизом; сообщения о новых проблемах принимаются по шаблону
`.github/ISSUE_TEMPLATE/bug_report.yml`.

## 1. Нет фоновых push-уведомлений

- **Причина:** сообщения передаются напрямую между устройствами (WebRTC DataChannel),
  а фоновый режим Android останавливает JavaScript в WebView. FCM-сервера и облачной
  истории в проекте нет осознанно: они вернули бы центральный сервер переписки.
- **Сейчас:** оба собеседника держат приложение открытым; исходящие сообщения ждут в
  очереди и уходят после возвращения получателя; статус «✓✓» означает сохранение у
  получателя. Ограничение явно указано в релизе, в приложении («Оба собеседника должны
  быть в приложении») и в этом файле.
- **План:** foreground-служба с постоянным уведомлением для удержания соединения
  (без FCM), затем — опциональный ретранслятор уведомлений по желанию пользователя.

## 2. Личность собеседника не проверяется криптографически автоматически

- **Причина:** у устройств нет заранее общих доверенных ключей; личный код передаётся
  пользователем (модель TOFU).
- **Сейчас:** код сверки (SAS) в меню чата: одинаковая строка `XXXX XXXX XXXX` на обоих
  устройствах подтверждает пару личных кодов; описана процедура сверки по доверенному
  каналу (RELEASE_NOTES.md, раздел «Сверка собеседника»).
- **План:** показ отпечатка ключа при первом контакте с явным предупреждением при его
  изменении; по возможности — сверка по QR при личной встрече.

## 3. Публичные signaling и STUN по умолчанию

- **Причина:** нужна работа «из коробки» без настройки серверов.
- **Сейчас:** по умолчанию `0.peerjs.com` и STUN Google/Cloudflare; в настройках можно
  указать свой signaling и TURN; инструкция и примеры конфигурации —
  `docs/SELF_HOSTING.md`. Публичные серверы видят только метаданные соединений.
- **План:** мастер первичной настройки с предложением своего сервера; документация
  развёртывания одним файлом (docker-compose).

## 4. APK не запускался на физическом устройстве в среде сборки

- **Причина:** в среде сборки нет SDK Android и образа эмулятора, домены загрузок
  заблокированы.
- **Сейчас:** проверены подпись (v2+v3), упаковка, состав APK; веб-часть покрыта 11
  браузерными сценариями, включая настоящий WebRTC-обмен; в CI добавлены Gradle-сборка и
  lint.
- **План:** прогоны на эмуляторе в CI (после восстановления доступа к образам), отчёт
  тестировщиков на реальных устройствах через шаблон issue.

## 5. Загрузка бинарных release-assets из среды сборки недоступна

- **Причина:** `uploads.github.com` обрывает соединение из этой сети (три повтора
  12.09.2026 без ответа).
- **Сейчас:** APK публикуется двумя способами: каталог `downloads/` тега (основная
  ссылка) и release-asset (зеркало, загружается в CI с повторами).
- **План:** публикация assets из GitHub Actions (там сеть GitHub доступна), ручная
  загрузка как запасной путь.

## 6. Нет звонков, групп, регистрации по телефону, восстановления аккаунта

- **Причина:** цель версии — надёжная переписка один на один без сервера.
- **Сейчас:** ограничение указано в релизе и в приложении.
- **План:** групповые чаты рассматриваются после устойчивого фонового режима; звонки —
  отдельный проект.

## 7. База шифруется ключом устройства, а не ключом от пароля пользователя

- **Причина:** прозрачное шифрование хранилища требует ключа, доступного приложению без
  ввода пароля. В 2.8.3 этим ключом служит мастер-ключ устройства: Android Keystore
  (StrongBox, когда доступен) или неизвлекаемый `CryptoKey` в браузере.
- **Сейчас:** в 2.8.3 записи базы шифруются AES-256-GCM (`{__libo:3, id, n, c}`,
  AAD `libo/db/v3|<id>`), бэкапы Android отключены (`allowBackup=false`), мастер-ключа в
  APK нет, PIN-замок использует PBKDF2-SHA-256 (310 000) и ограничение попыток.
- **План:** обёртка мастер-ключа ключом, производным от PIN/биометрии (чтобы данные были
  недоступны без пользователя), с понятной процедурой восстановления.

## 8. Экспорт не включает фотографии и не импортируется обратно

- **Причина:** экспорт задуман как текстовая копия для архива, а не как формат миграции.
- **Сейчас:** экспорт JSON содержит тексты, даты, направления и имена файлов фото.
- **План:** формат архива с фотографиями и импорт с проверкой контрольных сумм.

## 9. Серверные функции: регистрация по номеру, поиск людей, каналы, группы

- **Причина:** LIBO спроектирован как P2P без центрального сервера переписки; номерной
  поиск и каналы невозможны без каталога и ретранслятора.
- **Сейчас:** добавление по личному коду, QR и системным меню; группы и каналы отсутствуют
  осознанно, а не «сломаны».
- **План:** опциональный федеративный каталог контактов по выбору пользователя (вне
  ядра), групповые чаты после устойчивого фонового режима.

## 10. Лимит вложений 1,5 МБ и голосовые до 60 секунд

- **Причина:** прямое P2P-сообщение передаётся одним пакетом DataChannel; большие
  объекты требуют чанкинга с контрольными суммами, которого в протоколе v1 нет.
- **Сейчас:** лимиты честно указаны в подсказках кнопок и отклоняются с понятной ошибкой.
- **План:** протокол v2 с чанками и возобновлением передачи, после чего лимит вырастет
  до десятков мегабайт.

## 11. Архивы из резервных копий только для чтения

- **Причина:** восстановленные чаты не имеют живого собеседника и личного кода пары;
  отправка из архива выглядела бы отправкой «в никуда».
- **Сейчас:** архив помечен плашкой, компоновщик скрыт, звезда и поиск работают.
- **План:** импорт в живой чат при совпадении личного кода собеседника.

## 12. Слой безопасности 2.8.3 не проверен независимым аудитом

- **Причина:** внешний аудит требует сторонней команды и бюджета; проект развивается как
  тестовый релиз.
- **Сейчас:** вместо прежнего MT-слоя с AES-256 работает документированный E2EE v3
  (X25519 + Ed25519 + ChaCha20-Poly1305, Double Ratchet) на проверенных библиотеках
  `@noble/curves` и `@noble/ciphers`; 25 автотестов безопасности и 11 браузерных
  сценариев зелёные; требования и остаточные риски описаны в `SECURITY_ARCHITECTURE.md`,
  `docs/THREAT_MODEL.md`, `docs/SECURITY_AUDIT.md`, `docs/SECURITY_EVIDENCE.md`.
- **План:** внешний аудит криптографического слоя и протокола перед формулировками уровня
  «production security»; до аудита заявления ограничены тем, что подтверждено тестами.

## 13. Ротация ключа подписи в 2.8.0

- **Причина:** кейстор выпусков до 2.6.0 хранился вне Git на сборочной машине и
  потерян при её сбросе; подписать новый выпуск старым ключом невозможно.
- **Сейчас:** новый RSA-4096 ключ, отпечаток опубликован в RELEASE_NOTES.md;
  установка 2.8.0 требует удаления старой версии после экспорта копии.
- **План:** кейстор и пароль передать в секреты CI (HOW-TO-STORE-KEY.md), чтобы
  ключ больше не жил на одной машине и не мог быть потерян снова.

## 14. Ключ базы не привязан к код-замку и к биометрии

- **Причина:** замок проверяет PIN при запуске (PBKDF2-SHA-256, 310 000 итераций,
  ограничение 5 попыток в минуту), но мастер-ключ базы берётся из Keystore без участия
  пользователя, а ключ Keystore создаётся с `setUserAuthenticationRequired(false)`.
- **Сейчас:** замок скрывает содержимое от случайного доступа к устройству, а записи базы
  зашифрованы ключом устройства; в общих настройках Android доступен раздел «Android
  Keystore» в диалоге безопасности.
- **План:** привязка ключа к PIN/биометрии (`BiometricPrompt`,
  `setUserAuthenticationRequired(true)`) в следующей версии.

## 15. Отложенные сообщения уходят только при открытом приложении

- **Причина:** таймеры живут в JavaScript внутри приложения; фон и push-уведомлений в
  LIBO нет (см. пункт 1).
- **Сейчас:** срок хранится абсолютным временем, поэтому закрытие приложения не сдвигает
  отправку; пропущенные за время простоя сообщения уходят при следующем запуске, а
  сообщение можно отправить сразу или отменить.
- **План:** отправка из foreground-службы вместе с удержанием соединения.

## 16. Жесты и защита от скриншотов проверены косвенно

- **Причина:** среды сборки нет ни эмулятора, ни физического устройства, а свайп и
  двойной тап зависят от сенсора.
- **Сейчас:** жесты покрыты браузерным сценарием через настоящие pointer-события с
  `pointerType: 'touch'`, выбор реакции на двойной тап вынесен в чистую константу
  `DEFAULT_REACTION`, а переключатель «Защита от скриншотов» проверен на уровне вызова
  метода `setSecureScreen` моста Android.
- **План:** прогон на устройстве или эмуляторе, проверка `FLAG_SECURE` и инерции свайпа
  на реальном экране.

## 17. Argon2id недоступен в WebCrypto

- **Причина:** браузерный WebCrypto не предоставляет Argon2id, а собственная реализация
  KDF противоречила бы правилу «никакой самодельной криптографии».
- **Сейчас:** используется PBKDF2-SHA-256 с большим числом итераций (600 000 для
  серверного класса `Password`, 310 000 для локального PIN) и ограничение попыток.
- **План:** нативная (Android) или WASM-реализация Argon2id с проверенным происхождением
  и тестовыми векторами.

## 18. Серверных функций аутентификации нет

- **Причина:** сборка 2.8.3 — P2P без сервера переписки, поэтому нет аккаунтов,
  refresh-токенов, списка устройств, отзыва сессии на сервере, MFA и админ-API.
- **Сейчас:** у каждого устройства собственная идентичность; отзыв сессии и выход
  реализованы локально (`dropSession`, «Отозвать все сессии»); примитивы для серверного
  этапа (`Password`, `RateLimiter`, `SessionState`) уже написаны и протестированы.
- **План:** отдельный серверный релиз с аутентификацией, ротацией refresh-токенов,
  управлением устройствами и админ-API с MFA.

## 19. Метаданные видны сигнальному серверу, Tor-транспорта нет

- **Причина:** соединение устанавливается через сигнальный сервер PeerJS; скрыть факт,
  время и участников соединения без отдельной сети невозможно.
- **Сейчас:** содержимое переписки сервер не видит никогда (только конверты), можно
  поднять свой signaling/TURN (`docs/SELF_HOSTING.md`).
- **План:** абстракция транспорта с опциональным Tor/прокси и минимизация метаданных
  (padding, отложенная отправка).

## 20. Синхронная ротация цепочек требует доставки по порядку

- **Причина:** новая цепочка ключей выводится из текущего ключа цепочки, поэтому ротация
  синхронна, пока обе стороны получили все сообщения предыдущей генерации.
- **Сейчас:** транспорт — WebRTC DataChannel с доставкой по порядку и без потерь, что и
  требуется; при рассинхроне повторное рукопожатие создаёт новую сессию с чистым ratchet.
- **План:** хранить цепочки предыдущей генерации с ограниченным окном, чтобы принимать и
  потерянные сообщения предыдущего поколения.

## 21. Проверки Android Keystore и FLAG_SECURE не автоматизированы

- **Причина:** в среде сборки нет устройства и эмулятора Android.
- **Сейчас:** код моста `sealLocalSecret`/`openLocalSecret` и `setSecureScreen` собран и
  покрыт проверками уровня веб-слоя (выбор бэкенда `android-keystore`), но поведение
  системы подтверждается только на устройстве.
- **План:** инструментальные тесты на эмуляторе в CI, отчёт тестировщиков на реальных
  устройствах через шаблон issue.
