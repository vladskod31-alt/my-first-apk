# LIBO 2.8.3 — архитектура безопасности

Документ описывает **фактическую** реализацию слоя безопасности LIBO 2.8.3: какие
примитивы используются, как устроена иерархия ключей, как выглядит сетевой конверт,
что проверено автоматическими тестами и какие ограничения известны.

> Формулировка «система безопасна» здесь не используется: пока не выполнен внешний
> аудит, корректной является формулировка «реализованы проверенные механизмы и
> автоматические тесты, перечисленные ниже». См. `docs/SECURITY_AUDIT.md`.

Связанные документы:

- `docs/THREAT_MODEL.md` — модель угроз (угроза / атака / защита / остаточный риск);
- `docs/SECURITY_AUDIT.md` — чек-лист самопроверки;
- `docs/SECURITY_EVIDENCE.md` — таблица доказательств по каждой функции;
- `TESTING.md` — как повторить проверки;
- `KNOWN_ISSUES.md` — известные ограничения и план работ.

## 1. Что именно заменили в 2.8.3

В 2.8.2 переписка шифровалась самодельным слоем («MT-слой» с AES-256-GCM, выведенным
из общего пароля пары). В 2.8.3 этот слой **удалён** (`web/lib/mtproto.mjs` больше нет),
а вместо него реализован слой E2EE v3 (`web/lib/security.mjs`):

| Было в 2.8.2 | Стало в 2.8.3 |
| --- | --- |
| ключ пары выводился из общего секрета и не ротировался | рукопожатие X25519 + Double Ratchet |
| одно «поколение» ключей на весь чат | цепочка ключей на сообщение + ротация поколений |
| нет подписей отправителя | Ed25519-подпись идентичности и рукопожатия |
| нет защиты от повторов | окно повторов по `messageId` + время |
| ключи хранились как экспортируемые байты | неизвлекаемый мастер-ключ / Android Keystore |
| сообщения базы лежали открытым текстом | шифрование записей базы AES-256-GCM |

AES-256-GCM **остался** только на уровне локального хранилища (шифрование записей базы и
мастер-ключа), как и разрешено требованиями: сообщения в сети AES-GCM больше не шифруются.

## 2. Примитивы (только проверенные библиотеки)

| Задача | Алгоритм | Реализация |
| --- | --- | --- |
| Обмен ключами | X25519 (ECDH) | `@noble/curves 2.0.1` (`ed25519.js`, экспорт `x25519`) |
| Подписи | Ed25519 | `@noble/curves 2.0.1` |
| Шифрование конверта | ChaCha20-Poly1305 (AEAD) | `@noble/ciphers 2.1.1` |
| KDF | HKDF-SHA-256 | `crypto.subtle.importKey/deriveBits` (WebCrypto) |
| Хеши | SHA-256 / SHA-512 | WebCrypto |
| Пароль/PIN | PBKDF2-SHA-256, 600 000 итераций (серверный класс `Password`), 310 000 итераций (локальный PIN) | WebCrypto |
| Случайность | `crypto.getRandomValues`, `randomSecretKey` | CSPRNG ОС |
| Хранилище | AES-256-GCM, мастер-ключ из Android Keystore (StrongBox, когда доступен) или неизвлекаемый `CryptoKey` | `crypto.subtle`, `KeyVault` |

Запрещено и **не используется**: `Math.random`, самодельные PRNG, «своё» шифрование,
XOR-«шифры», зашитые ключи/пароли, повторное использование nonce, приватные ключи
открытым текстом. Argon2id в браузерном WebCrypto отсутствует; вместо него используется
PBKDF2-SHA-256 с большим числом итераций, а переход на Argon2id записан в план
(`KNOWN_ISSUES.md`).

## 3. Архитектура: полный стек LIBO

```
┌──────────────────────────────────────────────────────────────────────────────┐
│ UI (web/index.html, web/app.js)                                              │
│  • экран безопасности соединения  • код сверки  • PIN-замок  • FLAG_SECURE    │
├──────────────────────────────────────────────────────────────────────────────┤
│ Слой E2EE v3 (web/lib/security.mjs)                                          │
│  Identity · SecureSession · Ratchet · ReplayGuard · KeyVault · PairingToken  │
│  RateLimiter · SecureLogger · sanitizeError                                  │
├──────────────────────────────────────────────────────────────────────────────┤
│ Транспорт (web/lib/transport.mjs)                                            │
│  WebRTC DataChannel (DTLS) + сигнальный сервер PeerJS: sec-hello / envelope   │
├──────────────────────────────────────────────────────────────────────────────┤
│ Хранилище (web/lib/storage.mjs)                                              │
│  IndexedDB «libo-messenger-v2» · записи шифруются AES-256-GCM (ключ устройства)│
├──────────────────────────────────────────────────────────────────────────────┤
│ Платформа                                                                    │
│  Браузер: неизвлекаемый CryptoKey   Android: Keystore/StrongBox + FLAG_SECURE │
└──────────────────────────────────────────────────────────────────────────────┘
```

## 4. Путь сообщения: Identity → KEX → Session key → Encryption → Ciphertext → Transport

```
 1. Identity            Ed25519 (подпись) + X25519 (обмен) создаются на устройстве,
                        приватные ключи шифруются ключом KeyVault и не покидают его.
        │
 2. KEX (sec-hello)     X25519-эфемерный ключ + публичный ключ идентичности,
                        подпись Ed25519 по транскрипту
                        [libo/v3/hello, pairId, idPub, kxPub].
                        pairId = сортировка(свой код | код собеседника) — одинаков
                        у обеих сторон, поэтому подпись и соль ratchet совпадают.
        │
 3. Session key         HKDF-SHA-256: shared = ECDH(эфемер, эфемер собеседника),
                        salt = SHA-256(kxPubA | kxPubB | pairId),
                        root  = HKDF(shared, info = libo/v3/root).
                        Первый DH-шаг применяют обе стороны → корень и цепочки
                        совпадают без дополнительного пакета.
        │
 4. Encryption          Double Ratchet (Signal):
                          • DH-шаг на новых эфемерных парах X25519 — при смене
                            направления и при рукопожатии;
                          • цепочка ключей сообщений: HKDF(chain, info = message/key);
                          • ключ сообщения удаляется сразу после использования;
                          • ротация поколения цепочки после 200 сообщений или 12 часов
                            (детерминированно из ключа цепочки, см. §6).
        │
 5. Ciphertext          ChaCha20-Poly1305, nonce = 4 байта префикса цепочки + счётчик,
                        AAD = канонический заголовок конверта.
                        Подпись Ed25519 покрывает заголовок + шифротекст + тег.
        │
 6. Transport           { v:1, type:'envelope', version:3, messageId, conversationId,
                          senderKeyId, recipientKeyId, timestamp,
                          ratchet:{ dh, pn, n, gen }, nonce, ciphertext,
                          authenticationTag, signature } → WebRTC DataChannel (DTLS).
                        Сервер переписки отсутствует: доставлять конверт помогает только
                        сигнальный сервер, который видит адреса, но не содержимое.

 7. Получатель          подпись → окно повторов → AEAD → ratchet → валидация пакета → UI.
                        Любая ошибка = конверт отбрасывается, отправитель получает
                        событие отказа; открытый текст в сеть не уходит никогда.
```

## 5. Иерархия ключей

```
KeyVault (Android Keystore AES-256-GCM / неизвлекаемый CryptoKey)
   └── Identity  (на устройство)
        ├── Ed25519  — подписи рукопожатия и конвертов, отпечаток, код сверки
        └── X25519   — долговременный ключ идентичности (в текущем ratchet используется
                       эфемерными парами; долговременный ключ участвует в отпечатке)
   └── Мастер-ключ базы → AES-256-GCM для каждой записи (AAD: libo/db/v3|<id>)
   └── PIN-замок: соль + PBKDF2-SHA-256 (310 000) → сравнение через постоянное время
```

`keyId` — первые 16 hex-символов SHA-256 публичного ключа; отпечаток и «код сверки»
считаются по публичным ключам и не позволяют восстановить приватный ключ.

## 6. Ротация, срок жизни и rekey

1. **Лимит цепочки** — 200 сообщений (`LIMITS.MAX_CHAIN`), **срок жизни** — 12 часов
   (`LIMITS.CHAIN_MAX_AGE_MS`).
2. Новая цепочка выводится из текущего ключа цепочки:
   `newChain = HKDF(oldChain, salt = libo/v3/chain-salt, info = libo/v3/message/rollover)`.
   Так как цепочка отправки и цепочка приёма — это одна и та же цепочка, обе стороны
   получают одинаковый результат, а номер поколения `gen` уходит в подписанном заголовке.
3. Получатель, увидев `gen > текущего`, делает столько же шагов KDF, но не больше
   `LIMITS.MAX_GEN_AHEAD` (8) — завышенное поколение отвергается.
4. Ключ каждого сообщения удаляется сразу после использования; сохранённые «пропущенные»
   ключи ограничены (`MAX_SKIP` = 32) и привязаны к `gen|dh|n`.
5. Смена ключа идентичности собеседника останавливает сессию (`COMPROMISED`) и требует
   повторной сверки кода — это защита от подмены (MITM).
6. После переустановки приложения или смены устройства создаётся новая идентичность;
   собеседник видит предупреждение и подтверждает новый отпечаток.

Смена устройства/сессии на уровне аккаунта (список устройств, отзыв сессии, MFA,
административный API) относится к серверной части — в P2P-сборке 2.8.3 её нет, см. §9.

## 7. Состояния сессии

```
CONNECTING ──► CONNECTED ──► RECONNECTING ──► CONNECTED
     │              │               │
     └──────────────┴───────────────┴──► DISCONNECTED
CONNECTED / RECONNECTING ──► REVOKED        (кнопка «Отозвать все сессии», выход)
CONNECTED / RECONNECTING ──► COMPROMISED    (чужой/изменённый ключ, неверная подпись)
REVOKED / COMPROMISED — конечные состояния: приём и отправка прекращаются.
```

Переходы ограничены таблицей `ALLOWED_TRANSITIONS`; попытка недопустимого перехода
отклоняется. В интерфейсе состояние видно в диалоге «Безопасность соединения».

## 8. Что реализовано на устройстве

- **Приватные ключи** создаются на устройстве, шифруются `KeyVault` и не экспортируются
  из него; в APK ключей нет.
- **Android Keystore**: `MainActivity.sealLocalSecret/openLocalSecret` — AES-256-GCM,
  StrongBox при наличии, ключ неизвлекаемый, `setUserAuthenticationRequired(false)`
  (биометрическая привязка — в плане).
- **Base данных**: каждая запись `{ __libo:3, id, n, c }` — AES-256-GCM с AAD
  `libo/db/v3|<id>`; открытого текста сообщений, паролей и токенов в базе нет.
- **FLAG_SECURE**: включается для экранов с приватными ключами, кодом восстановления,
  настройками безопасности и секретными чатами (переключатель «Защита от скриншотов»).
- **QR**: содержит только одноразовый короткоживущий токен сопряжения
  (`PairingToken`, хеш хранится локально). Пароль, приватный ключ, мастер-ключ и
  refresh-токен в QR не попадают.
- **SecureLogger**: секреты (ключи, токены, пароли, nonce, цепочки) вырезаются, в
  релизной сборке отладка выключена; пользователю показываются только безопасные
  сообщения (`sanitizeError`), стек-трейсы и внутренние пути не выводятся.
- **Ограничение частоты**: `RateLimiter` (5 попыток/60 с для PIN, 60 сообщений/60 с для
  отправки) — защита от перебора и флуда.
- **Сверка контакта**: отпечаток ключа и «код сверки» в диалоге безопасности, кнопка
  «Подтвердить ключ»; при смене ключа — предупреждение и остановка сессии.

## 9. Чего в 2.8.3 нет (честно)

| Пункт | Состояние | План |
| --- | --- | --- |
| Сервер аутентификации (регистрация, сессии, refresh-ротация, отзыв устройств, MFA, админ-API) | нет: сборка P2P, аккаунтов нет | отдельный серверный релиз; класс `Password`, `RateLimiter`, состояния сессий уже готовы к подключению |
| Argon2id | нет (WebCrypto не поддерживает) | нативная реализация или WASM с проверенным кодом |
| Tor / альтернативный транспорт | нет | абстракция транспорта описана, реализация — в плане |
| Защита от анализа метаданных (padding, mix-net) | нет: сигнальный сервер видит пары адресов | план работ |
| Биометрическая привязка ключа (BiometricPrompt) | нет: ключ Keystore без биометрии | `setUserAuthenticationRequired(true)` в следующей версии |
| Внешний аудит кода | не проводился | критично перед заявлениями о «production security» |
| Синхронизация истории между устройствами | нет (и это осознанно: у каждого устройства свой ключ) | план работ |

## 10. Проверки

```
npm test                      # 55 тестов: 30 core + 25 security
npm run test:e2e              # 11 end-to-end сценариев (в том числе E2EE между двумя клиентами)
node --test tests/security.test.mjs    # только слой безопасности
```

Тесты безопасности проверяют: шифрование/дешифрование, обмен ключами, аутентификацию
(подписи), ротацию и срок жизни ключей, отзыв сессии, шифрование базы, испорченный
шифротекст, повтор, повторное использование ключа/nonce, MITM, перебор, повреждённые и
чрезмерные конверты, истечение токена сопряжения, смену ключа идентичности, отсутствие
утечек в логах и сообщениях об ошибках. Полная таблица — `docs/SECURITY_EVIDENCE.md`.
