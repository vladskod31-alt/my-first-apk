# 🔐 LIBO SECURITY — архитектура 2.8.2

Документ фиксирует целевую архитектуру защиты и честно отмечает, что из неё
**реализовано в 2.8.2**, что **частично**, а что остаётся **дорожной картой**.
Правило проекта: не заявлять систему безопасной, пока автоматические тесты
безопасности не проходят (`npm test` → `tests/e2ee.test.mjs`, `npm run test:e2e`).

## Поток сообщения

```text
QR Pairing ──► Identity Verification ──► X25519 (3-DH) ──► Double Ratchet ──► ChaCha20-Poly1305
   │                 │                        │                  │                    │
   │  код + Ed25519  │ подпись hello,          │ IK/EK обеих       │ корневая цепочка,   │ ключ сообщения
   │  + токен        │ пин ключа (TOFU / QR)   │ сторон            │ DH-шаг на ответ     │ используется один раз
   ▼                 ▼                        ▼                  ▼                    ▼
Encrypted Message ──► WebRTC DataChannel (DTLS) ──► Recipient ──► Decrypt (проверка AAD, окно пропусков ≤ 200)
```

### Рукопожатие

1. При открытии канала обе стороны шлют `e2-hello`: `ik` (X25519 identity), `sk`
   (Ed25519), `ek` (эфемерный X25519), `sig = Ed25519(SHA-256("libo-e2ee-hello-v1" | от | кому | ik | ek))`
   и, при наличии, одноразовый токен приглашения `tok`.
2. Подпись привязывает ключи к паре личных кодов и направлению: hello нельзя
   переиграть другому собеседнику или в обратную сторону (тест «swapped direction»).
3. Приложение сравнивает `sk` с закреплённым ключом контакта:
   - ключ из QR-приглашения не совпал → соединение отклоняется («возможна подмена»);
   - ключ изменился по сравнению с прошлым → баннер «Ключ безопасности изменился»,
     статус доверия сбрасывается;
   - первый контакт → ключ закрепляется (TOFU), пока пользователь не сверит номер.
4. Общий секрет: `HKDF-SHA-256(DH(IK_a,EK_b) ‖ DH(EK_a,IK_b) ‖ DH(EK_a,EK_b))`.
   Инициатор — меньший личный код; он делает первый DH-шаг и сразу шлёт
   зашифрованный `ping`, чтобы обе стороны могли отправлять без ожидания.

### Рэтчет и шифр

- Корневой KDF: `HKDF-SHA-256(salt = RK, ikm = DH, info = "libo-e2ee-rk-v1")` → `RK', CK`.
- Цепочка: `MK = HMAC(CK, 0x01)`, `CK' = HMAC(CK, 0x02)`.
- Ключ и nonce сообщения выводятся из `MK` через HKDF (`"libo-e2ee-msg-v1"`, 44 байта).
  `MK` используется ровно один раз, поэтому пара (ключ, nonce) не повторяется.
- AAD = `"libo-e2ee-ad-v1" | код инициатора | код ответчика | IK_init | IK_resp | заголовок(dh, pn, n)`.
- Заголовок: 32 байта DH-ключа + `pn` + `n` (uint32). Пропущенные ключи хранятся до
  200 на цепочку и 600 на сессию; повтор уже использованного ключа отклоняется.
- Состояние продвигается только после успешной аутентификации — подделанный пакет
  не рассинхронизирует пару (тест «state survived the failed attempt»).

### Совместимость и защита от даунгрейда

- Собеседник на 2.8.1 не шлёт `e2-hello`; канал работает как раньше (MT-слой
  AES-256-GCM поверх DTLS). Как только сторона увидела `e2-hello`, открытые
  прикладные пакеты от неё игнорируются, а отправка без готовой сессии не
  происходит (сообщение остаётся в очереди).

## Локальное хранилище

- Все записи чатов и ключи устройства пишутся в IndexedDB как `{iv, ct}` —
  AES-256-GCM, метка записи в AAD. Записи 2.8.1 переносятся при первом запуске.
- Ключ хранилища:
  - Android: случайные 256 бит, обёрнутые AES-GCM-ключом из Android Keystore
    (StrongBox при наличии, иначе TEE/программный); в IndexedDB лежит только
    обёртка;
  - браузер: неизвлекаемый `CryptoKey` WebCrypto.
- Код-замок: PBKDF2-SHA-256 (120 000 итераций), растущая задержка после трёх
  ошибок, автоблокировка по таймеру, биометрия через системный `BiometricPrompt`.
- `FLAG_SECURE`, `allowBackup=false`, правила извлечения данных запрещают перенос.

## Правила безопасности проекта

- Не изобретать криптографию — только аудированные примитивы (`@noble/*`, WebCrypto)
  и опубликованные конструкции (X3DH-подобное рукопожатие, Double Ratchet).
- Не хранить закрытые ключи открытым текстом; не отправлять их на сервер; не класть
  ключи и пароли в QR; не слать открытый текст на сервер.
- Никакого `Math.random()` для секретов — только CSPRNG ОС (`crypto.getRandomValues`).
- Не переиспользовать nonce; ротировать ключи; фиксировать смену identity-ключа.
- Защита от повтора (счётчики рэтчета и `msg_id` MT-слоя), MITM (подпись, пин ключа,
  номер безопасности), перебора (PBKDF2 + задержка) и перехвата сессии
  (эфемерные ключи на соединение, отзыв сессий).
- Чувствительные буферы обнуляются, когда это возможно в JS.
- Система не считается безопасной, пока не проходят `tests/e2ee.test.mjs`
  и сценарии `tests/app.spec.mjs`. Независимого аудита не было.

## Известные ограничения 2.8.2

- Bluetooth P2P и Tor не реализованы (см. дорожную карту выше).
- Пароль TURN хранится в настройках без отдельного шифрования (наследие 2.8.x).
- Обнуление памяти в JavaScript не гарантирует отсутствие копий в куче движка.
- Веб-слой не может использовать аппаратный ключ напрямую для E2EE-операций:
  Keystore защищает ключ хранилища, а не сами операции X25519/Ed25519.
